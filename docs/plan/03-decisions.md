## ADR-001 Scope: one main pathology, pre-clinical technical validation

- **Context.** The analysis recommends one main pathology and a pre-clinical technical validation without real patients (analisi §5, §9 item 0.2). The workshop paper uses hypertension as its running example.
- **Decision.** The main pathology is hypertension (antihypertensive dosing with blood-pressure response). Validation is semi-synthetic plus ROS 2 simulation plus an optional mock-ward demo. No real patients. This is stated in the abstract, introduction and limitations (analisi §10 objection 1).
- **Alternatives.** Two pathologies from the start (diabetes with the simglucose simulator is the analysis' optional second case, §5.8); a clinical pilot (out of reach and out of scope).
- **Consequences.** WS04 targets hypertension only; the second pathology is an optional task (ADR-019). Human confirmation of scope is task WS00-T02.
- **Status.** accepted (analisi §9 item 0.2) (confirmed (WS00-T02, 2026-10-08)).

## ADR-002 C3 reduced to integrity violations with a threat model

- **Context.** "Adversarial tampering" is not identifiable from low confidence, and an informed attacker injecting plausible, cross-modally consistent data is undetectable by construction (analisi §3.6, §4.5, §4.8, §10 item 4).
- **Decision.** Class C3 is renamed and claimed as "integrity or plausibility violations" against declared attack classes (BLE injection and replay without keys, physical access to the dispenser, perception spoofing). Out of scope: compromised robot, RSM or specification. The diagnosability matrix reports the undetectable cases as a result.
- **Alternatives.** Keep "tampering" and claim general adversarial detection (rejected: not defensible).
- **Consequences.** WS02 owns the threat model and matrix; WS04 injects C3 at two attacker-knowledge levels (naive and informed); WS08 reports the non-detectable rows.
- **Status.** accepted (analisi §3.6, §9 item 0.2) (confirmed (WS00-T02, 2026-10-08)).

## ADR-003 Distributed architecture: ward node plus robot

- **Context.** An RSM only on the robot is a single point of failure, loses BLE streams when the robot leaves the room, and cannot serve N patients (analisi §2 R3 weakness 2, §4.9 item 1).
- **Decision.** A fixed ward node (BLE gateway plus RSM for continuous φ_CP monitoring) supervises the robot with a heartbeat. The robot runs the embodied specifications (task deadlines, presence and intake witness) and provides evidence. If the robot is unavailable, the fallback escalates to the nurse. The auditability claim is kept ("single auditable verification path") with a watchdog added.
- **Alternatives.** Robot-only RSM (rejected: R3 fatal); ward-only RSM (rejected: robot loses its role and A4 has nothing to measure).
- **Consequences.** Contract `#ros-2-interfaces` encodes placement. The robot's contribution stays central because it executes the obligations induced by the specification (φ_resp, φ_sched) and is the only witness channel.
- **Status.** accepted (analisi §4.9 item 1, §9 item 0.2) (confirmed (WS00-T02, 2026-10-08)).

## ADR-004 DISPENSE is distinct from INTAKE

- **Context.** A dispenser opening does not prove intake (analisi §4.9 item 5, §8.1).
- **Decision.** Two signals: `DISPENSE` (device) and `INTAKE` (verified by the robot). The witness channel is the only source of `INTAKE`.
- **Alternatives.** Treat opening as intake (rejected: hides the main adherence weakness).
- **Consequences.** Templates use dispense for hold and count, and intake for response evidence where present. The double-take versus bounce confounder depends on dispenser content sensing (analisi §4.5 matrix).
- **Status.** accepted.

## ADR-005 PriorSource interface with a literature implementation first

- **Context.** MIMIC-IV and eICU access requires PhysioNet credentialing (course, data use agreement) and can take days to weeks; it is on the critical path (analisi §5.1, §9 item 0.6). The user's answer at bootstrap: access not yet started.
- **Decision.** All benchmark parameters flow through `PriorSource`. `LiteraturePriorSource` uses values from published literature with mandatory `source_ref` per parameter. `MimicPriorSource` (and an eICU variant for the shift test) is added when access exists. Public-access data (VitalDB, MIT-BIH noise stress test database, BIDMC, PhysioNet/CinC 2015) can be used immediately for noise and artefact modelling.
- **Alternatives.** Wait for MIMIC before starting WS04 (rejected: blocks the critical path); invent parameters (rejected: forbidden by PROMPT precedence).
- **Consequences.** Results produced before MIMIC access are labelled "literature priors"; WS08 repeats key experiments with MIMIC priors once available. Human owner: WS00-T04.
- **Status.** accepted.

## ADR-007 Past-time formulation and derived signals for counters

- **Context.** Future operators block immediate verdicts; counters "outside STL" break uniform σ and ξ (analisi §4.1, §4.7, §2 R1 weaknesses 5 and 6).
- **Decision.** Constraints are written in past-time STL (once, historically) so each obligation is evaluated at its deadline with a bounded latency. Counters are derived signals with atomic predicates (robustness `limit - count`). "Pressure decrease" uses a derived pre-dose signal `bp_pre`; the freeze operator (STL*) is cited as an alternative but not implemented. Point-event windows use `O[W, W+T_s]`.
- **Alternatives.** Future-time STL with bounded eventually plus look-ahead buffering; STL* freeze.
- **Consequences.** WS01 documents the equivalence to the future-time form (ablation A7). Time robustness is used for timing constraints.
- **Status.** accepted (analisi §4.1).

## ADR-008 Three-valued verdicts; conformal prediction only in PENDING

- **Context.** The workshop text contradicts itself on whether conformal envelopes or measured values ground the verdict (analisi §4.3).
- **Decision.** Definitive verdicts come only from the measured prefix with robustness intervals (unknown future replaced by physiological bounds). Conformal prediction acts only in the PENDING state and produces early warning. Definition of ρ by verdict type as in analisi §4.4. The predictive component targets continuous signals and robot care-delivery deadlines rather than five-a-day blood pressure.
- **Alternatives.** Conformal envelope on measured values (rejected: suppresses true positives near thresholds); pure anomaly detection (rejected: what the paper moves away from).
- **Consequences.** Proposition 1 (WS01) gives the one-sided guarantee; A1 and A2 ablations test the components.
- **Status.** accepted (analisi §4.3, §4.4, §4.7).

## ADR-009 Normalised robustness and lexicographic ranking

- **Context.** Robustness in mmHg, ms and doses cannot be combined by `min` (analisi §4.2).
- **Decision.** Per-predicate normalisation `clip(sigma / s_pi, -1, 1)` with clinician-fixed scales; ranking lexicographic by clinician priority then σ̃; never normalise by conformal interval width. AGM robustness and weighted STL are cited as alternatives; ordinal NEWS2-style bands as another.
- **Alternatives.** As listed.
- **Consequences.** Scales and priorities live in the parameter registry; ablation A3 measures the effect; optional clinician-ranking agreement study in WS11.
- **Status.** accepted.

## ADR-010 Attribution: hierarchical rules with abstention

- **Context.** κ has no producing module and C2/C3 identifiability is undefined (analisi §4.5).
- **Decision.** Start with the hierarchical auditable rule (integrity → C3, else system → C2, else coherent clinical → C1, else UNDETERMINED). Six evidence groups form the `EvidenceVector`. Cascades propagate a root cause. A Bayesian variant is optional.
- **Alternatives.** Probabilistic network first (rejected: harder to audit, needs benchmark-fit probabilities).
- **Consequences.** UNDETERMINED is a valid, scored output; the diagnosability matrix is a machine-readable artefact; A4 removes the witness channel.
- **Status.** accepted.

## ADR-013 RTAMT as reference STL tool

- **Context.** The analysis lists RTAMT, Breach and S-TaLiRo and says "RTAMT o custom" for the monitor (analisi §3.1, §9 item 5, B3 uses RTAMT).
- **Decision.** Original proposal: RTAMT is the reference implementation wrapped behind `ralmon.spec` and `ralmon.monitor`; a custom monitor may replace it if RTAMT cannot express robustness intervals or sparse sampling. Updated by WS05-T02 after the spike: the evaluator is custom and RTAMT is not a dependency of the monitor (outcome C, see below).
- **Alternatives.** Custom monitor from the start; Breach or S-TaLiRo (MATLAB dependence); outcome B (custom evaluator, RTAMT kept as test oracle and as the engine of baseline B3), not adopted for the reasons in the record.
- **Consequences.** The spike result is recorded in `docs/plan/workstreams/WS05-monitor/rtamt-spike.md`. `ralmon.spec` and `ralmon.monitor` do not import RTAMT; no `rtamt` extra is added to `pyproject.toml`; WS06-T04 builds baseline B3 on `make_point_evaluator` and the paper says that its point-robustness evaluator is the project's own (the wording "same templates with RTAMT" of analisi §5.4 is not used).
- **Status.** accepted (confirmed (WS00-T02, 2026-10-08)).

Spike result (WS05-T02, closes the spike of ADR-013): outcome C. Tested RTAMT 0.4.10 on Python 3.12.8 (host throwaway venv) and 3.12.15 (`ralmon-dev` container, same report); on Python 3.14.4, the Python of the repository, `import rtamt` fails (`No module named 'typing.io'`). Q1 FAIL (4 of 7 templates translate mechanically and equal the goldens; `sched` and `int` contain `age`, `sys` uses an equality atom that RTAMT evaluates as `-abs(a - b)`), Q2 PASS, Q3 NOT-SUPPORTED (`update` returns a point value; the endpoint rule is unsound for `range`, `count` and `sys`), Q4 FAIL (no guard rule, no unknown value), Q5 FAIL (8 of 10 time-margin goldens only with hand rewrites), Q6 PASS (operator updates linear in the instances, but each timed `once` or `historically` scans its window at every step). Outcome C is forced by the Q1 failure (rule of WS05-T02 check 9). Entry point that WS06-T04 must call for raw robustness: `make_point_evaluator` of `ralmon.monitor`, created by WS05-T04. Evidence and the reasons for not adopting outcome B: `docs/plan/workstreams/WS05-monitor/rtamt-spike.md`. This remains `[DA-CONFERMARE]` until a human confirms it.

## ADR-021 Contract-gap register: amendments are decided at M1 [DA-CONFERMARE]

- **Context.** During phase F6 the fourteen workstream authors, reading `02-interfaces.md` against analisi, reported gaps and ambiguities. None was edited during authoring, because contracts change only through an ADR. The reports concern:
  - `Template`, `Verdict`, `Alert`: the unit of mixed-atom templates (HOLD, RESP, SYS), the treatment of sigma = 0, the range of `sigma_norm` and the direction of `priority`, the "possible" variant needing a lower quantile, whether `creates_robot_obligation` also holds for INT, a measurement-count template, `VerdictRecord` without a sub-formula path or predicted severity, `Detection` without a template field, the attributed cause of predicted alerts;
  - `EvidenceVector`: no field for dispenser content or dispense interval (needed for the double-take versus bounce rows of analisi §4.5), `seq_gap_or_replay` mixing message loss (C2) and replay (C3), no clock-health field, undefined key of the evidence mapping, and no owner for building an `EvidenceVector` from an observed day and a verdict record;
  - `Trace schema`: impulse signals are events only, no carry-over across midnight, no benchmark reader;
  - `PriorSource`: `PatientParams`, `AdherenceParams` and `DeviceErrorModel` lack fields the generator needs;
  - `Conformal calibrator`: no model-version token for the recalibration rule, `CalibrationEpisode` tied to `TemplateId` and normalised sigma while B4 and B5 work on other residuals, `sigma_true` wording versus the rule that detectors fit on training ground truth only;
  - `Metrics` and `Experiment config`: `Matching` undefined, no first-decidable instant in `GroundTruthEvent`, no alpha grid, bootstrap settings or shift conditions, macro-F1 and abstention rate without a function;
  - `Signals`: no robot ETA or task-queue signal for deadline forecasting; `Time and units`: no time-compression rule for the lab demo;
  - `Package public API`: names used elsewhere but missing (`TimeMs`, `DurationMs`, `Forecaster`, `Forecast`, concrete monitor and attributor, `Matching`, four metrics functions, a benchmark reader, a factory for the proposed detector "ours").
- **Decision.** (a) The public-API omissions are editorial and are added now (contract `Package public API` moves to 0.1.1); the semantic gaps are not edited during bootstrap. (b) Each semantic gap is resolved by the owning task through a proposed ADR, and all are consolidated at the M1 freeze: WS01-T08 resolves the template, verdict and alert points (its README lists them as CP1 to CP13), WS02-T03 the evidence points, WS04-T02 the prior and trace points, WS05-T01, T04, T06 the monitor, calibrator and cycle points, WS08-T01 the metrics and experiment points, WS07-T03 and WS10-T04 the time-compression rule. (c) No implementation task that consumes a gap may start before the ADR of the owning task is `accepted`; the owning tasks precede consumers in `depends_on` (see ADR-023).
- **Alternatives.** Edit `02-interfaces.md` now (rejected: guesses would bypass the owning workstreams and the clinician review); ignore (rejected: agents would diverge).
- **Consequences.** Contract versions bump at M1. Agents reading a contract before M1 must also read this ADR and the "contract points" section of the owning README.
- **Status.** proposed [DA-CONFERMARE].

## ADR-024 Package public API reconciliation (0.1.1 to 0.2.0) [DA-CONFERMARE]

## ADR-025 Trace file format and benchmark directory layout [DA-CONFERMARE]

- **Context.** Contract `02-interfaces.md#trace-schema` rule 3 leaves the file format (JSON or Parquet) to WS04-T01 and requires it to be recorded as an ADR. The bit-for-bit reproducibility rule of `01-conventions.md` section 3 needs byte-identical output for equal input, and the ground-truth discipline needs a detector run that never reads the truth.
- **Decision.** Canonical JSON (`ralmon.benchmark.trace`): sorted keys, two-space indent, final newline, floats written with `repr`, non-finite numbers rejected, no timestamp or host field. Observed files and truth files live in different directories, a refinement of contract rule 3 that keeps `truth/` out of every detector run; an observed file has exactly the keys `patient_id`, `day_index`, `seed`, `samples`, `events`, `care_plan_id`, and the writer refuses a payload key that contains `latent` or `ground_truth`. Plans go to `plans/<care_plan_id>.json` (owner WS04-T11, not part of this decision).

- **Consequences.** WS04-T02 to WS04-T12, WS06, WS07-T03 and WS08-T01 read and write through `ralmon.benchmark.trace`. Sequences read back are tuples, so compare with tuples. No contract signature changes; the trace-schema contract version is unchanged.

## ADR-030 Conformal quantiles: lower quantile for the "possible" variant and exact rank rule [DA-CONFERMARE]

- **Context.** WS01-T06 (`docs/formal/06-rho-proposition1.md`, open points CP4 and section 10) found two tensions with the contract `#conformal-calibrator` and `#verdict`. (1) Contract rule 2 of `#verdict` and analisi §4.4 write the "possible" variant with the symmetric form `sigma_hat - q_{1-alpha} < 0`, which is valid only if the score law is symmetric (sufficient, not necessary); the bound that holds for any exchangeable score law is Proposition 1b with the lower quantile `q^lo_alpha`, `P(sigma_tilde < 0 and sigma_hat + q^lo_alpha >= 0) <= alpha`. (2) The quantile ranks `k = ceil((n+1)(1-alpha))` (upper) and `floor((n+1) alpha)` (lower) are wrong in floating point: the product `(n+1)*(1-alpha)` gives 577 wrong upper and 49 wrong lower ranks over 98,901 pairs (n from 1 to 999, alpha from 0.01 to 0.99), exact arithmetic on the binary value of the float alpha is wrong in 1,280 pairs each way, and the integer rule on the decimal literal (`Fraction(repr(alpha))`) is wrong in none. A level computed in floats (for example the Bonferroni allocation `alpha_total / n_tests`) can still have a 16 to 17 digit repr and a wrong rank (358 of 231,884 pairs, always conservative); it must be computed as `Fraction(repr(alpha_total)) / n_tests` and passed as a fraction.
- **Decision.** Proposed: adopt Proposition 1b (lower quantile `q^lo_alpha`) as the definition of the "possible" variant, with a `quantile_lower` method (or the existing `quantile` on episodes with `sigma_hat` and `sigma_true` swapped); take alpha as the decimal literal and compute ranks with integer or `Fraction` arithmetic; pass allocated levels as fractions. The "likely" variant and its guarantee string are unchanged.
- **Alternatives.** Keep the symmetric form and state symmetry as a hypothesis of the guarantee string (valid only under symmetry; the document shows a 41-of-152 exact-cell failure for an asymmetric law); round the product with `ceil(round(x, 9))` (0 wrong ranks on the two-decimal grid, untested on allocated levels).
- **Consequences.** WS05-T06 (test 2 float-boundary remark: `10 * (1 - 0.3)` is exactly 7.0 and the boundary level is 0.7, so `quantile(0.7)` on its fixture is 0.0; step 3 rounding; test 8 symmetric reading, `sigma_hat = 0.3` is not emitted by the lower-quantile form) and WS05-T08 (test 7) carry a note and stay `blocked`; WS01-T08 records the contract amendment at the freeze. No signature of `02-interfaces.md` changes in this ADR beyond the added method.
- **Status.** proposed [DA-CONFERMARE].

## ADR-035 Trace schema: evidence conventions for `Event.payload`, the gateway verification outcome, `auth` Samples and the availability of the robot channels

## ADR-039 PK/PD response: one-compartment plus Emax behind `ResponseModel`, Pulse not adopted, sign convention of the effect [DA-CONFERMARE]

- **Context.** WS04-T04 needs the drug response of the latent patient (analisi §5.1 item 1) and was asked to evaluate the Pulse Physiology Engine as an alternative, adopting it only if its substance library holds the antihypertensive anchored in the registry (ADR-020: no agent names a drug). `docs/benchmark/pulse-evaluation.md` records that this could not be evaluated: no installation or documentation exists locally and the agent has no network access. ADR-038 gap G6 left the unit of `ec50` and the sign of `emax_mmhg` open; this task composes the response with the latent pressure and so fixes both in practice.
- **Decision.** Proposed: the custom one-compartment oral absorption plus Emax model with linear superposition over the true intakes (`OneCompartmentEmax` in `src/ralmon/benchmark/pkpd.py`) is the default engine of the benchmark generator, used through the `ResponseModel` protocol (`effect_mmhg(params, intake_times_ms, t_grid_ms, intake_scales=None)`). The Pulse Physiology Engine is not adopted for now; it is revisited only when a human answers the three questions of `docs/benchmark/pulse-evaluation.md` (matching antihypertensive in the library and the same source as the custom parameters, licence, run time for 1400 patient-days). A Pulse-backed engine would be a new implementation of `ResponseModel`, not a change to any caller. Conventions fixed here and in effect (for confirmation, and for the `#priorsource` 0.2.0 comments of ADR-038 (b)): (1) the concentration is per unit dose (`D / V = 1`) and `ec50` is dimensionless in the same normalised units, a literature EC50 in physical units being converted by the human in the `rationale` of its provenance row; (2) the effect is a pressure DECREASE magnitude `>= 0` in mmHg and the composition is `sbp = baseline - effect`; `emax_mmhg >= 0` (a negative value is an error, not an increase); (3) per-intake scales `s_i >= 0` scale the Emax of intake `i` as `Emax * s_i * C_i / (EC50 + C_total)`, so that a scale of 0 is a non-response whose drug still occupies the saturation term; (4) the onset window of one intake is the set of integer milliseconds at which the effect is at least the threshold, returned rounded inward, or `None` when no millisecond reaches it. Old version: none (no contract signature changes). New version: none. Affected tasks: WS04-T06, WS04-T09, WS04-T10, WS04-T11 (they call the model or the window), and WS04-T02's reading of `ec50` and `emax_mmhg` (consistent with it). Migration: none; when ADR-038 is accepted the sign and unit text above goes into the comments of `PatientParams`.
- **Alternatives.** Adopt Pulse now (rejected: its library, licence and run time are unverified, and the anchored drug is unknown to the agent); a signed `emax_mmhg` with a negative decrease (rejected: the contract field is a magnitude "maximal drug effect" and the composition would need a sign flip at every caller); scaling the dose instead of the Emax for the non-response injection (rejected: a halved dose does not halve the effect, the task fixes the Emax scaling); a float-tolerance bisection for the onset window (rejected: integer bisection on the same predicate that the tests evaluate gives exact bounds).
- **Consequences.** The benchmark's drug response is a declared simplification (one compartment, no inter-dose accumulation beyond superposition, no tolerance, no coupling to heart rate). Results are labelled with the unverified literature priors (ADR-020) until a human fills and verifies the PK/PD rows. The window checks of WS04-T10 compare the registry's Δ1 and Δ2 with the modelled window through `window_overlap`.
- **Status.** proposed [DA-CONFERMARE].

## ADR-041 Alert field semantics: sigma_norm of violated and predicted alerts, kappa of predicted alerts, t_ms, score, label, sub-formula path and alert lifecycle [DA-CONFERMARE]

- **Context.** WS01-T07 (`docs/formal/07-alert-tuple-mapping.md`, section 9: CP5, CP13, OP-T07-1, OP-T07-2, OP-T07-3, OP-T07-5, OP-T07-6, OP-T07-9, OP-T07-10, OP-T07-17) found that `02-interfaces.md#alert` 0.1.0 leaves the meaning of several fields open: (a) what `sigma_norm` carries for a VIOLATED alert whose interval has a finite upper end (T04 OP-14) and for a predicted alert (T04 OP-4, OP-15); (b) the kappa of a PREDICTED_VIOLATION alert, because attribution "turns violated records into alerts" while `Alert.verdict` admits PREDICTED_VIOLATION (CP13); (c) the meaning of `t_ms`, `score`, `label` and `xi.subformula_path`, and the identity and lifecycle of an alert whose record changes state (PREDICTED_VIOLATION to VIOLATED or SATISFIED, refinement records, cascade links); (d) which alerts feed the attribution metrics of WS08 (E3 and E4). No signature changes, but the meaning of fields does, and the rule of `CLAUDE.md` is that a change of meaning needs an ADR (ADR-028 to ADR-030 were opened for changes of the same kind).
- **Decision.** Proposed, as statements of meaning with no signature change. (1) `sigma_norm` is the normalised bound that decided the emission of the alert: `N_s(hi)` of the first VIOLATED record, frozen at emission (T05 section 3.7), and `clip(sigma_hat + q, -1, 1)` for a predicted alert (T06 section 2.4); both are in `[-1, 0)`. For SCHED, `hi = -T_s` only when the closing step is after the deadline (`H_i > k_d`); otherwise `hi = -inf` and `sigma_norm = -1`. (2) The kappa of a predicted alert is UNDETERMINED by definition (`label` too, `xi.evidence_used` empty); the test on the verdict state is made by `attribute_all`, and `AttributionRule.attribute` stays independent of `state`; the definitive alert carries the kappa of the rule at the cut-off of the first VIOLATED record. (3) `t_ms` is `decided_at_ms` of the first VIOLATED record (`t_eval_ms` for a predicted alert); `label` equals `kappa`; `score` is minus `sigma_norm`. (4) The identity of an alert in a care plan is `xi.instance_key`; a supersession (PREDICTED_VIOLATION to VIOLATED) and a cascade link are new values with the same identity, the predicted alert stays in the history, a refinement record issues no alert, an alert closed by SATISFIED is a false predictive alarm, and an alert whose instance stays undecided is unresolved. (5) `xi.subformula_path` names the decisive sub-formula, with the guard marker recoverable; listing the other violated sub-formulas needs a joined string written by the monitor. (6) For the attribution metrics of WS08 the label of a pair matched by a predicted alert is read from the alert of the same instance that supersedes it, and a matched pair with no superseding alert is excluded from the numerator and the denominator of E4 and reported as a count. Old version: `#alert` 0.1.0. New version: 0.1.1 (comments of the dataclass fields only) if adopted.
- **Alternatives.** The point forecast `clip(sigma_hat, -1, 1)` as the severity of a predicted alert (range `[-1, 1]`, CP5 left open); `-1` with a guard marker as the severity of a SCHED violation (asserts a full scale that no lemma certifies); re-issuing the violated alert at each refinement (moves a shown alert in the ranked list); a provisional kappa for a predicted alert from the same rule, or restricted to C2 and C3 (unsound for the case of a late robot, whose evidence is stamped at the deadline); a separate alert type for early warnings (a new contract).
- **Consequences.** Affected tasks: WS02-T04 (check 8 and step 5: the section on predicted violations), WS05-T07 (tests 3, 5, 18, 20), WS05-T04 step 8 (the carrier fields `predicted_sigma_norm` and `subformula_path`), WS05-T08 (the log of `sigma_hat`, `q`, `alpha`, `n` and the variant), WS08-T01 and the WS08 README E3 and E4 (scoring of attribution), WS11-T02 (the rendering), WS01-T08 (the ranking fixtures RK-1 and RK-4 of `ranking.yaml` hold the refined value -0.7 and are to be relabelled or regenerated). By ADR-021 (c) these tasks carry a note and no implementation task that consumes the rules starts before the ADR is accepted. Migration: none for data; the golden fixtures RK-1 and RK-4 change label only. The open points that the ADR does not settle are listed in section 9 of the document (the carrier fields, the closure of a predicted alert, the contract wording of "violated records").
- **Status.** proposed [DA-CONFERMARE].

## ADR-044 Attribution: declared channels for the C1 exclusion, and the scope of the sequence and time evidence to the robot's presence stream [DA-CONFERMARE]

- **Context.** `docs/models/attribution-rule.md` (WS02-T04, open points OP-AR-1 and OP-AR-2) found two consequences of the evidence conventions of `docs/models/evidence-channels.md`. (a) C1 is claimed by exclusion, so every channel of the template's exclusion set must be available and denied (invariant I4: no certainty from missing data). In the reference profile S6 of the evidence-channels document (no diagnostics reports, no declared deadline, no independent clocks) `system.diagnostics_ok`, `system.qos_deadline_missed` and `crypto_temporal.timestamp_implausible` are `None`, and EC-OP-19 records that the last cannot be denied in a benchmark without a transport-delay model; C1 is then unreachable for every template: C1 recall zero and abstention one on matched clinical events, with C2 and C3 unaffected. The rule cannot tell a channel the profile does not have from a channel that failed: the contract field is `None` for both. (b) EC D-12 limits `crypto_temporal.*` and `system.ble_link_quality` to the BLE device streams; the hazard CAS-5 (a violated INT caused by a lost or late `presence` sample) is therefore resolved in the rule by not reading the witness pair as integrity evidence, and the third option of D-12 (widen the scope to the robot's presence stream) was not adopted. ADR-036 (device capability profile) is proposed and gives the extractor the capabilities per source; the rule does not read it.
- **Decision.** Proposed: (1) the benchmark and simulation profiles declare the capabilities of the cuff path (diagnostics, a data-stream deadline for the periodic cuff stream, independent clocks with a transport-delay model for the BLE devices) and the generators emit the corresponding reports (WS04-T06, WS04-T07, WS04-T11, WS07-T03); (2) `HierarchicalRule` takes, besides its four thresholds (`hr_coherence_tolerance`, `ecg_sqi_floor`, `ppg_sqi_floor`, `ble_link_quality_floor`), the set of channels that the profile declares, as canonical `group.field` paths; when it checks the C1 exclusion set a channel that the profile does not declare is not applicable instead of unavailable, and an asserted reading of an undeclared channel still counts as evidence; with every channel declared the rule is the rule of `attribution-rule.md`. The signature of `attribute` and of `Attributor`, `#evidencevector` and `#attribution` are not changed; what changes is the meaning of `None` for an undeclared channel inside the rule, which amends ADR-036 (the profile is also an input of the rule). Checked exhaustively: on vectors where the undeclared fields of S6 are always `None` the combinations that reach C1 are 0 with the rule of `attribution-rule.md` and 18 for `range`, 2 for `sched`, 18 for `hold` and 90 for `resp` with the declared-channel set, and the checks of invariant I4 give the same results as for the rule of the document (the one exception is `crypto_temporal.authenticated`). The exception of variant B is an undeclared `crypto_temporal.timestamp_implausible`, which a device without independent clocks can still assert (never deny; EC-OP-19): masking that asserted reading turns an abstention into C1, in 18, 2, 18 and 90 combinations of `range`, `sched`, `hold` and `resp` (hypothesis H-18 of `attribution-rule.md`); `system.diagnostics_ok` and `system.qos_deadline_missed` cannot be asserted without a declared capability. (3) The scope of the sequence and time evidence is not extended to the robot's presence stream (D-12 stays); the option is recorded as an alternative.
- **Alternatives.** Keep the rule as it is and only report the limit (C1 recall zero on a profile that does not declare the channels; the cheapest and the most conservative; rejected as the sole answer because the limit would be produced by what the profile declares); declare the capabilities only (decision (1) alone; sufficient where the generators can emit the reports, not where a capability is absent by design, for example a device without message authentication or a robot without a battery model); drop `system.diagnostics_ok`, `system.qos_deadline_missed` and `crypto_temporal.timestamp_implausible` from the exclusion set (rejected: where diagnostics or a deadline are declared, replacing an asserted reading by `None` would turn C2 into C1, against invariant I4; variant B keeps them required where declared and has an exception only for an asserted undeclared timestamp field); widen `crypto_temporal.*` and `system.qos_deadline_missed` to the robot's presence stream (reverse of EC D-12; changes the A4 statement that `crypto_temporal.*` is unchanged, needs an extractor change, and does not close CAS-5 for a loss that no later message reveals).
- **Consequences.** Affected tasks: WS02-T04 (the rule document keeps the rule without the declared-channel set until this ADR is accepted), WS02-T05 (the matrix outcomes per profile), WS04-T06, WS04-T07, WS04-T11, WS07-T03 (declarations and emitted reports), WS05-T07 (the constructor of the rule and the extractor profile), WS08-T04 (A4 reported per profile). Neither (1) nor (2) makes C1 reachable for `measurement_refusal` (`sched`) in the benchmark as generated, for an `evidence_margin_ms` that admits no earlier cuff traffic, nor for `double_take` or `dose_omission` (`count`): a `sched` violation, and a guard-failed `hold` or `resp`, leaves the cuff silent in the evidence window, so the cuff-derived fields are `None` unless other cuff traffic lies between `evidence_margin_ms` before the tick and the cut-off (`evidence_grace_ms`), and `count` needs the dispenser evidence of ADR-032. No signature of `02-interfaces.md` changes in this entry; amendments are decided at M1 (ADR-021).
- **Status.** proposed [DA-CONFERMARE].

## ADR-050 `rank_alerts` order K1: VIOLATED before PREDICTED_VIOLATION inside a priority [DA-CONFERMARE]

- **Context.** ADR-028 (accepted) adopts the order key `K0 = (priority, sigma_tilde, t_ms, instance_key)` and leaves `K1`, which places VIOLATED alerts before PREDICTED_VIOLATION alerts inside a priority, "to be settled by WS01-T05". `05` does not settle it, and `04` section 4.5 and OP-3 hand the proposal to WS01-T08 after the clinician's view of the trade-off. Under `K0` a predicted alert with severity -0.5 precedes a VIOLATED alert with -0.2 of the same priority (golden `ranking.yaml` RK-5, `literal_contract`). Because the severity of a predicted alert is a conformal bound that moves with the calibration (`07` section 1.5), `K0` lets a forecast displace a certified violation in the list a nurse reads.
- **Decision.** Proposed. Old text (`02-interfaces.md#template` 0.1.0, `rank_alerts`): `"""Lexicographic order: template priority first (clinician-assigned), then sigma_tilde ascending within a priority."""`, refined by ADR-028 to the key `K0 = (priority, sigma_tilde, t_ms, instance_key)`. New text: `"""Lexicographic order: template priority first (clinician-assigned), then the verdict class (VIOLATED before PREDICTED_VIOLATION), then sigma_tilde ascending, then t_ms and xi.instance_key."""`, that is `K1(a) = (priority ascending, verdict class ascending, sigma_tilde ascending, t_ms ascending, instance_key ascending)` with the verdict class VIOLATED = 0 and PREDICTED_VIOLATION = 1. The golden file RK-5 records both orders (`literal_contract` for `K0`, `recommended_extension` for `K1`) and the lemmas of `04` section 4.2 hold with the verdict class as the second component.
- **Alternatives.** Keep `K0` (the order is by severity alone; a forecast of a severe deviation ranks before a certified mild one); no early-warning alerts in the ranked list (a separate list for early warnings: a new output).
- **Consequences.** Old version: `#template` 0.1.0 (docstring of `rank_alerts`, with ADR-028). New version: folded into the `#template` bump of ADR-045 (0.2.0), or 0.1.1 if this ADR is accepted alone. Affected tasks: WS05-T03 (`rank_alerts` and its property tests P-R1 to P-R6 with the verdict as a read field), WS05-T07, WS08 (ablation A3 reports the order), WS09-T04. The cost, stated: a forecast of a severe deviation ranks after a certified mild one inside the same priority; that is a clinical trade-off for the reviewer. Migration (`01-conventions.md` section 6): the bump and the edit of the docstring are made in the commit that accepts this ADR; the tasks that list `#template` in `interfaces` are found by grep and updated in that commit; until accepted `rank_alerts` implements `K0`; the worked day (`patient-day.yaml`) has no predicted alert in the final set and is unaffected. No signature changes. `02-interfaces.md` is not edited by WS01-T08.
- **Status.** proposed [DA-CONFERMARE].

## ADR-051 Care-plan signature scheme: HMAC-SHA256 over a canonical serialisation, behind the `PlanVerifier` interface [DA-CONFERMARE]

- **Context.** The sources fix no signature scheme for the distributed care plan: analisi §4.9 item 7 asks only for "firma e versioning" so that "the robot only evaluates specifications it cannot author or modify", and review item R1-W9 (integrity and versioning of the distributed specification) asks for the check at load. `docs/formal/07-alert-tuple-mapping.md` section 4 fixes what must be signed (the canonical serialisation of every `CarePlan` field except `signature`, so that a field added later is signed without a change of the definition), the load-time behaviour (signature, exact `registry_version`, `plan_version` not lower, signature required in a ward deployment) and the limits (OP-T07-12 (f), (h), (i)). WS05 README D8 names HMAC-SHA256 as the placeholder scheme behind a `PlanVerifier` interface; the Package public API (ADR-024) lists `PlanVerifier`, `HmacSha256PlanVerifier`, `PlanIntegrityError` and `verify_plan` without signatures. The threat model (WS02-T02) excludes a compromised specification, authoring or key.
- **Decision.** Proposed. (1) Scheme: HMAC (RFC 2104) with SHA-256 over the canonical bytes of the plan, written in `CarePlan.signature` as the lowercase hexadecimal digest (64 characters; an uppercase, short, long or non-hexadecimal text is not a valid signature, so a signature has one text form). Standard library only (`hmac`, `hashlib`, `json`), comparison with `hmac.compare_digest`. Interface: `PlanVerifier.verify(payload: bytes, signature: str) -> bool`; `HmacSha256PlanVerifier(key: bytes)` with `sign(plan) -> str`; an empty key, or a key that is neither `bytes` nor `bytearray` (a `bytearray` is accepted and copied), is refused and no minimum length is invented; `verify_plan(plan, verifier, *, registry_version=None, require_signature=False) -> None` raises `PlanIntegrityError` for a signature that does not verify, a registry version that differs (exact string equality, as docs/formal/03 section 5.2), an unsigned plan when a signature is required, and a signed plan when no verifier is configured (never accepted silently); it checks the signature, not the well-formedness of the plan, so an unsigned plan is not serialised and a malformed unsigned plan passes (the monitor checks the plan itself, WS05-T04), while a signed plan is serialised first and a plan that cannot be serialised raises. (2) Canonical bytes (`ralmon.spec.integrity.canonical_plan_bytes`): one JSON object holding every field of `CarePlan` except `signature` (the fields are taken from `dataclasses.fields`, so a new field is signed), keys sorted by code point at every level, separators `,` and `:` with no whitespace, UTF-8 without ASCII escaping; sequences keep their order and a list and a tuple are the same; integers are integers in the signed 64-bit range (a bool, a float or a larger integer is refused); the values of `param_values` are written as floats whatever the Python type (`2` and `2.0` sign alike), by the shortest round-trip text of the Python float, so `-0.0` and `0.0` are two contents; NaN and infinities are refused; a `TemplateId` is written as its value; a plan that cannot be serialised raises `PlanIntegrityError`. (3) The golden digests of the tests come from `openssl dgst -sha256 -hmac` over canonical bytes written by hand (`tests/fixtures/spec/make_plan_golden.sh`), not from the code under test. (4) Limits, stated and not hidden: the key is shared, so whoever can verify can also sign, and "the robot and the ward node cannot author or modify a plan" holds by role and configuration, not by the scheme (OP-T07-12 (i)); the scheme covers accidental corruption and modification in transit by a party that holds no key, not a compromised back-end, authoring, key or insider (threat model, Exclusions); it cannot see a replay of an old signed plan at an equal `plan_version`, and the rule that `plan_version` never decreases belongs to the monitor that loads the plan (WS05-T04; OP-T07-12 (h)); the template library and the registry file are bound to the plan only by the `registry_version` string and are not signed; the form is not RFC 8785 (JCS), so a back-end in another language must reproduce the canonical text of the golden files, in particular the float text; key generation, distribution, rotation and revocation are a deployment matter. No claim of security assurance for a deployment is made.
- **Alternatives.** An asymmetric signature (for example Ed25519 through a cryptography library): the verifier cannot forge, which enforces "cannot author" by the scheme, but it adds a dependency and a key distribution problem (a public key per ward, revocation) that the project does not need for a pre-clinical technical validation; the `PlanVerifier` interface keeps it possible as a second implementation without a change in `verify_plan` or in the monitor. A standard envelope (JWS or COSE): more tooling, a larger surface, no gain for this scope. No signature (rejected: R1-W9 asks for one and the interface costs little). A signature that also covers the registry digest (the plan would then pin the file, not only the version string; open point OP-14 of docs/formal/03, deferred).
- **Consequences.** No signature of `02-interfaces.md` changes: the names are in the Package public API since ADR-024 and the contract `#template` already has `CarePlan.signature` and `registry_version`. Affected tasks: WS05-T04 (`Monitor.load` calls `verify_plan`, refuses a lower `plan_version`, sets `require_signature=True` in a ward deployment), WS04-T11 (the plan builder signs with the benchmark key and stores the signature in `plans/<care_plan_id>.json`), WS07 (the signed plan on `/ralmon/care_plan`), WS13 (the limits above go into the release notes). If ADR-045 (c) is accepted (`CarePlan.schedule` becomes a sequence of `ScheduleTick`), the encoder of `schedule` changes (it accepts integers only) and every plan signed before the change is invalid; the same holds for any change of the canonical text. The exact registry version match means that every registry bump, a patch included, requires the plans to be issued again (docs/formal/03 section 5.2, OP-9).
- **Status.** proposed [DA-CONFERMARE].

## ADR-053 Monitor core surface of WS05-T04: `run_offline` keyword-only arguments, `push_availability`, `PointEvaluator` entry point and the named errors [DA-CONFERMARE]

- **Context.** WS05-T04 builds the measured half of the monitor against `02-interfaces.md#monitor` 0.1.0, which has three gaps that tests of the formal goldens expose. (1) `MonitorConfig` carries only the string `registry_version`, so `run_offline` cannot obtain the registry, the template library or a plan verifier; the monitor needs all three (the physiological bounds, the window parameters, the verification of a signed plan). (2) The golden cases of `docs/formal/golden/verdicts.yaml` that state `channels_unavailable` (CP6, `05` section 3.5) have no carrier in `Sample` or `Event`: an absent presence sample cannot be told from a robot channel that is known to be down, and the verdict differs (`undecidable: channel_unavailable:presence` against `value_undefined:presence`). (3) ADR-013 (accepted, outcome C) says that baseline B3 builds on `make_point_evaluator`, and the Package public API lists `PointEvaluator` and `make_point_evaluator` without a signature. ADR-013 is not edited by WS05-T04; its Consequences already name the entry point, and the signature is recorded here.
- **Decision.** Proposed. Old text is quoted verbatim from `02-interfaces.md#monitor` 0.1.0 and the Package public API 0.2.1.
  - (a) Old (`run_offline`): `def run_offline(day: ObservedDay, plan: CarePlan, config: MonitorConfig, calibrator: ConformalCalibrator | None, forecaster: Forecaster | None) -> Sequence[VerdictRecord]: ...`. New: the five parameters are unchanged (the monitor annotates `day` with the structural `ObservedTrace` of ADR-024) and three keyword-only parameters with default `None` are added: `registry` (default `load_registry(step_ms=config.step_ms)`), `templates` (default `load_templates(registry=registry)`) and `verifier` (default no verifier; a signed plan then raises `PlanIntegrityError`, as `verify_plan` of ADR-051). A caller that passes the five positional arguments keeps working.
  - (b) Old (`Monitor` protocol): the five methods `load`, `push_sample`, `push_event`, `advance`, `verdict_latency_bound_ms`. New: the protocol is unchanged. `StreamingMonitor` adds, outside the protocol, `push_availability(signal, available, t_device_ms, t_rx_ms)` (the seam of CG-6: `signal` is `presence` or `intake`, the channel is available until marked, the mark is ordered by device time with the samples and events and is late by the same rule R-late), `late_inputs()`, `rejected_inputs()`, `stats()` and `close()`. The constructor keywords are `calibrator`, `forecaster`, `verifier`, `template_ids`, `require_signature` and `buffer_capacity`; `calibrator` and `forecaster` accept any object and are never called (WS05-T08 gives them a role), and a predictive `MonitorConfig` (`predictive=True`) raises `MonitorConfigError` until then. `run_offline` does not call `push_availability`: an `ObservedTrace` has no availability stream. Consequence, corrected in fix round 1 (the first text called a trace replay "the conservative reading"): a missing presence sample reads as `value_undefined:presence` only BEFORE the first presence sample; after a sample the level is held, so a trace with no availability mark and no zero-valued presence sample (what the benchmark generator emits, WS04-T06 test 11) leaves every later dispense witnessed by the old sample. `push_availability` also ends the held level of `presence` (ADR-054, proposed): the level belongs to one co-location episode. `stats().presence_samples_without_availability_marks` is the gate for the hazard (non-zero exactly when presence samples were used and no availability mark for `presence` ever arrived) and `stats().presence_level_older_than_window_steps` is information only; ADR-054 holds the options.
  - (c) Old (Package public API, `ralmon.monitor`): `PointEvaluator`, `make_point_evaluator` without signatures. New: `make_point_evaluator(template: Template, instance: TemplateInstance, registry, step_ms: int, *, anchor_kind: str | None = None) -> PointEvaluator`, where `PointEvaluator` has `step(t_ms, values) -> float | None` (steps are consecutive from 0, `None` for an unavailable channel and a missing or NaN entry for an undefined one, the result is the raw robustness in `Template.unit` at the decision step and `None` before it), a read-only `unit` and `guard_failed` (the guard marker of the decision, or `None`). `anchor_kind` is one of `measurement` (RANGE, SYS), `dispense` (HOLD, RESP, INT, COUNT limit), `sched_tick` (SCHED) or `day_end` (the COUNT day-end obligation); it defaults to the first kind of the template and a kind that the template does not admit raises `MonitorConfigError`. Baselines B3 and B5 (WS06-T04, WS06-T05) call it; it delegates to the instance classes that the monitor uses, so a baseline and the monitor cannot disagree on a point value given the same `values`. The caller builds `values`: the `presence` entry it passes is the level of the current co-location episode (absent from the step at which the channel returns until the first new sample, `None` while the channel is down), which the evaluator cannot check.
  - (d) Old (Package public API, `ralmon.monitor`): `MonitorConfigError`, `PlanVersionError`. New: `ralmon.monitor` also exports, outside `__all__`, `PlanFeasibilityError` (a `MonitorConfigError` raised for a plan whose anchor is already finalised, whose window parameters are off the grid or whose `param_values` override is outside the registry range), `MonitorInputError` (a refused argument of `push_*`, `advance` or `push_availability`), `MonitorInvariantError` (an internal check on the interval, never raised for valid input; it passes through `advance`, `run_offline` and the point evaluator and is never reported as a bad argument), the carriers `MonitorStats`, `RejectedInput`, `ChannelAvailability`, and, for the attribution layer and the experiments, `run_offline_detailed(...) -> OfflineResult` (the records of `run_offline` plus `late_inputs`, `rejected_inputs` and `stats`; `run_offline` keeps the contract signature and returns the records only) and `resolve_subformula_path(template, path) -> str` / `resolve_subformula_paths(template, path) -> tuple[str, ...]` (the text of the decisive sub-formula, or of every part of a composite `subformula_path` whose parts are joined by `;`, ADR-048 (a)); all are outside `__all__`, importable from the package root as WS05-T03 did for the extras of `ralmon.spec`, until this ADR is accepted. Every public entry point raises only `MonitorConfigError` (and its subclass `PlanFeasibilityError`), `PlanVersionError`, `PlanIntegrityError`, `MonitorInputError` and `MonitorInvariantError`, including for hostile arguments; the entry points are the package-root names and the boundary functions of `formula`, `parameters`, `config`, `evaluator` and `offline` (`tests/monitor/test_public_api.py` sweeps every function of every `__all__`, every public function of every module and of the package root, and the methods of `ReorderBuffer`, `Formula` and `PathTable`; `tests/monitor/test_field_fuzz.py` replaces one field at a time of `MonitorConfig` and a subclass of it, `Sample`, `Event`, `CarePlan`, `TemplateInstance`, `Template`, a day and its items and a registry object); only the classes built by the monitor itself from validated values (`instances.*`, `EngineContext`, `StepView`, `WitnessTracker`) are not entry points, and a test classifies every class. `VerdictState('junk')` raises the stdlib enum `ValueError` and the stubs of WS05-T08 raise `NotImplementedError`, by design. `PlanFeasibilityError` is NOT a `PlanIntegrityError` or a `PlanVersionError` (an untrusted plan and a trusted plan that cannot run are different causes), so a caller that catches only those two (the task text of WS05-T09 for `rsm_node`) must also catch `MonitorConfigError`. The typing differs from the contract in one place: `calibrator` is `object | None` where the contract says `ConformalCalibrator | None`, because the layering rule of this package (it imports `ralmon.signals` and `ralmon.spec` only) forbids the import; `forecaster` is `Forecaster | None`.
  - (e) The minimal behaviour of ADR-047 (g) is implemented now so that a plan cannot move a clinical parameter silently: a `TemplateInstance.param_values` entry that differs from the registry value must be listed in `registry.overrides()` and lie inside the stated range, otherwise `PlanFeasibilityError`. ADR-047 stays proposed; if it is amended the check follows it.
  - (f) `VerdictRecord` carries the four trailing fields of ADR-048 (a) (`undecidable`, `guard_failed`, `subformula_path`, `predicted_sigma_norm`) AHEAD OF THE CONTRACT until ADR-048 is accepted; the nine fields of `#verdict` 0.1.0 are first, verbatim and in order, and a test compares them field by field. The records of this task have `predicted_sigma_norm = None`.
  - (g) New counters of `MonitorStats`, ahead of the contract like the rest of the class: `dedup_evicted_count` (duplicate keys evicted at the capacity, after which a replay of the evicted sequence number is accepted), `anchors_without_plan` (measurement and dispense anchors that arrived before any plan was loaded and created no instance) `presence_level_older_than_window_steps` (information: finalised steps at which the level in force is older than `int_window`; positive even with correct marks when a visit lasts longer than the window), `presence_samples_without_availability_marks` (the gate of ADR-054), `ignored_samples` (samples of the monitor-generated `day_end` signal, which the benchmark generator also writes) and `plan_instances_before_start` (plan instances anchored before the first step of the run, see (h)).
  - (h) `run_offline` runs the day `day_index` from the step `day_index * K` (the benchmark writes the days of a patient on one continuing axis, `day_index * T_day + clock time`, WS04-T06; the contract text of `TimeMs`, "since the start of the patient-day trace", reads as the same axis only for day 0): the monitor starts there (package-private `_start_at`), plan instances anchored before it are skipped and counted, inputs stamped before it are reported as finalised. A day written on the per-day axis with `day_index >= 1` is therefore reported (every input rejected with a reason), not swallowed; a bad `day_index` is a `MonitorInputError`. Open for the plan owner (WS04-T11): the axis of `TimeMs` in the contract text.
- **Alternatives.** Put the registry and the library in `MonitorConfig` (changes a frozen dataclass of the contract and ties it to objects that are not plain data); a global registry (hidden state, breaks the test with the F0 fixture); carry the availability in `Event` (a new `EventKind` is a contract change for a case that only the robot knows); a mutable status flag on the monitor (not ordered with the stream, so not causal).
- **Consequences.** Old version: `#monitor` 0.1.0 and Package public API 0.2.1. New version: `#monitor` 0.2.0 (item (a) and the notes of (b), (c)) and Package public API 0.2.2 (item (d)), made in the commit that accepts this ADR; `#verdict` is bumped by ADR-048, not here. Affected tasks: WS05-T05 to WS05-T09 (the feature, evidence and ROS 2 wrapper tasks read `stats()` and `push_availability`; T08 adds the calibrator and the forecaster behind the same constructor), WS04-T10 to WS04-T12 (the benchmark calls `run_offline` with the registry and templates of the benchmark), WS06-T04 and WS06-T05 (`make_point_evaluator`), WS08 (the experiments pass `registry` and `templates` explicitly and read `stats()`). ## ADR-054 Presence witness: the level of a robot visit, outages of the channel and a trace that carries no zero [DA-CONFERMARE]

- **Context.** The review of WS05-T04 (round 1, finding B1) showed that INT is satisfied by an old `presence` sample in two ways. Reproducer 1: `presence = 1.0` at 07:00, the channel marked unavailable at 07:10 and available again at 20:55, a DISPENSE at 21:00 gave INT SATISFIED, interval `[300000, 300000]`, from a 14-hour-old observation. Reproducer 2: the same without any availability mark. The second is what the benchmark generator emits: `docs/plan/workstreams/WS04-benchmark/tasks/T06-measurement-process.md` test 11 requires presence samples of `1.0` at robot arrivals only and no zero-valued sample (contract `#signals` rule: "absence is reported through the EvidenceVector, not as a value of zero"), and its own test `test_delayed_dose_outside_visit_is_not_witnessed` (a dose after the dwell has "no INTAKE and no presence") passes through `run_offline` as `int@29700000 satisfied [300000, 300000]` (reproduced in fix round 1 with that fixture; 955 steps with a level older than `int_window`, and `presence_samples_without_availability_marks` positive). Every dispense after the first robot visit of a generated day is then INT-satisfied, so the C3 injections that rest on INT (dispense forgery) and the A4 ablation would be blind. The normative documents do not agree. (1) `docs/formal/02-templates.md` section 4.7 ("Presence is a level") and TG-9: `presence` is a status level held between samples, the age of the witness is the time since the last step with `presence = 1`, "a witness that has left needs an explicit `presence = 0` sample, as in the fixtures G-INT-1 and G-INT-2"; TG-9 adds that if the robot node emits `presence` only while it observes the patient, "the trace needs the availability mask of T01 CG-6 or an event kind (WS02 and WS05-T02)". The patient-day golden does so (an explicit `0.0` at 06:59 and the channels unavailable at all other times). (2) `02-interfaces.md#signals` (rule) and `01-signals-sampling.md` sections 2.2, 2.4 and 3.5: `presence` and `intake` "exist only while the robot is co-located"; `w` is unavailable whenever the robot is not co-located and never converted to 0; no zero marks a departure. (3) `docs/models/evidence-channels.md`: H-MASK (availability of both robot channels is the robot status, the last `NODE_STATE` report with `payload.colocated`), H-INIT (a run starts with the robot not co-located) and the rule "a presence level is held: the level at a step is the value of the latest accepted PRESENCE sample whose visible step is not after it", which reads the level across an outage. (4) `01` section 3.2 holds a sample until the next one and says nothing about outages; the independent oracle of WS05-T04, written from `01`, `02` and `05` only, therefore held the level across an outage, and the first version of the monitor did the same. No task emits the `NODE_STATE` report with `colocated` (WS04-T06 Notes, M2: owner to be assigned, proposed WS04-T11), and `ObservedTrace` has no availability stream, so `run_offline` marks nothing. The documents cannot all be right; the conflict is between 02 section 4.7 / TG-9 (an explicit zero or a mask), the `#signals` rule and WS04-T06 test 11 (no zero), and the extractor of evidence-channels (a level held across an outage).
- **Decision.** Proposed. Implemented provisionally in fix round 1, so that the monitor is not silently wrong where it can know better: the monitor reads the contract rule "exists only while co-located" literally for the level, that is **the held level of `presence` belongs to one co-location episode**. A step at which the channel is marked unavailable (`push_availability`) clears it; after the channel returns the level is undefined (NaN) until a new sample arrives, which INT reads as `value_undefined:presence` (PENDING with the marker, never SATISFIED and never VIOLATED on the old sample); a sample that arrives while the channel is down is not held after the return. Reproducer 1 is now PENDING `[-49560000, 300000]` with the marker `undecidable: value_undefined:presence`. The oracle (`tests/fixtures/monitor/oracle.py`) encodes the same reading with a comment that it is a reading of the contract rule and not a sentence of `01` section 3.2. This does NOT fix reproducer 2: a trace with no mark and no zero keeps the level of the last visit, the documented behaviour of `02` section 4.7, pinned by `tests/monitor/test_witness.py::test_documented_hazard_a_trace_without_zeros_or_marks_witnesses_every_later_dispense`, and `MonitorStats.presence_samples_without_availability_marks` is the gate: it is non-zero exactly when presence samples were used and no availability mark for `presence` ever arrived (a result that rests on INT is evidence only if it is 0 or the trace carries the explicit zeros of option (a); a result that reports it non-zero is not). `presence_level_older_than_window_steps` stays as information: it counts the finalised steps at which the level in force is older than `int_window`, and it is positive even on a correct trace with marks, because the generator's visit lasts 10 minutes and `int_window` is 5. Options for the remaining conflict, with the recommendation: **(a)** the trace carries an explicit `presence = 0.0` at robot departure (or a `NODE_STATE` report); this follows `02` section 4.7 and the golden, needs the `#signals` rule amended (a departure is not "the robot sees no patient", so the `0` is a stand-in for an unavailability) and WS04-T06 test 11 changed. **(b)** the monitor derives the availability of both robot channels from the `NODE_STATE` reports with `payload.colocated` (H-MASK, H-INIT, one mask for both channels), as `run_offline` and the ROS 2 node would; with the episode rule above this is the whole design of the evidence-channels document, `push_availability` is its seam, the contract needs no change (`NODE_STATE` and `payload.colocated` are in the evidence vocabulary), and the A4 ablation needs the same reports to mask the channel. It needs an emitter: WS04-T06/T11 write `NODE_STATE colocated` true at each arrival and false at each departure (the visits are in `ObservedStream.visits`), WS07 writes them live, and `run_offline` reads them. The `channels_unavailable` entries of the goldens stay (they are the harness form of the same mask). **(c)** presence is an observation valid for a declared window (an impulse, or a level valid for `presence_validity` steps after the sample): no mark and no zero is needed and the generator output is right as it is; it changes the semantics of `01` section 3.2 and `02` section 4.7 (the INT template and its hand calculations), adds a parameter that needs a registry entry and a clinical review (ADR-020), and makes the explicit zero of the patient-day golden redundant. Recommendation: **(b)** with the episode rule, because it is what H-MASK and H-INIT already say, it keeps the contract and the golden, it is required anyway by A4 and by `witness.robot_present`, and the monitor does not invent a validity time; (a) is a fallback for a robot that stays co-located and stops seeing the patient (this case needs the explicit zero of `02` section 4.7 under every option); (c) only if the clinician wants a validity time. Until the choice is made and the emitter exists, every INT-based result computed on a generated day is not evidence.
- **Alternatives.** Keep the literal hold of `01` section 3.2 across outages (the first version of the monitor: reproducer 1 stays SATISFIED); clear the level at departure only when a `NODE_STATE` report says so (that is (b)); read a stale level as `value_undefined` after `hold_lookback` steps (a variant of (c) with an existing parameter, but `hold_lookback` is the HOLD look-back of a measurement and not a validity time of a robot observation).
- **Consequences.** No signature of `02-interfaces.md` changes under the decision above; under (a) the `#signals` rule changes (text), under (c) `01` section 3.2 / `02` section 4.7 and the registry (a new entry). Affected tasks, with the hand-overs appended to their Notes: WS04-T06 (done; its output makes INT blind after the first visit; its test 11 and the `NODE_STATE colocated` emitter, M2), WS04-T11 (the builder emits what the chosen option needs), WS05-T08 and WS05-T09 (who reads `NODE_STATE colocated` and calls `push_availability`; the `rsm_node` and the offline path must produce the same mask), WS05-T07 (`witness.robot_present` reads the level across an outage in `evidence-channels.md` EX-5; align it with the episode rule), WS06-T04 and WS06-T06 (build `presence` per episode when calling `make_point_evaluator`), WS08-T04 (A4 and dispense forgery results depend on it; gate on `presence_samples_without_availability_marks == 0`). **Known divergence between the provisional clearing of the monitor and the extractor of `evidence-channels.md`**: the extractor holds the level across an outage ("the latest accepted PRESENCE sample whose visible step is not after it"), the monitor clears it. Example: `presence = 0.0` at 06:00, the channel down from 06:10 to 20:50, a dispense at 21:00 with no INTAKE and no `auth`: the extractor gives `witness.robot_present` False and `witness.intake_observed` False, so invariant I2 of EX-9 expects the INT instance VIOLATED, while the monitor says PENDING `value_undefined:presence`; and invariant I4 (a PENDING instance with that marker has `witness.robot_present` not False) fails for the pair. The tests of WS05-T07 that take the invariants of EX-9 from a monitor run will see it. It is closed by adopting the episode rule in the extractor (the level of a window step is the latest sample of the current co-location episode, otherwise undefined) or by reverting the monitor to the literal hold; this ADR does not decide it. `tests/monitor/test_witness.py::test_known_divergence_with_the_extractor_of_evidence_channels` pins the monitor side. The monitor tests that pin the provisional behaviour are in `tests/monitor/test_witness.py`; the oracle comment says where the reading comes from. Migration: when the ADR is accepted, the choice is implemented in the commit that accepts it and the pinned hazard test is replaced by the test of the chosen option.
- **Status.** accepted (decision of gab, 2026-10-09): option (b) with the episode rule. The availability of `presence` and `intake` comes from the robot `NODE_STATE` reports with `payload.colocated`, one mask for both channels; the held level of `presence` belongs to one co-location episode; the extractor of `docs/models/evidence-channels.md` reads the level with the same rule, which closes the known divergence. Migration: not in this commit. The change needs tests first and must leave the traces without reports (the goldens) unchanged, so it is the new task WS05-T11 (translation inside `StreamingMonitor.push_event`, so that `run_offline` and the ROS 2 node share it; replacement of the pinned hazard test; amendment of EX-5). WS04-T11 writes the reports from `ObservedStream.visits`; WS08-T01 depends on WS05-T11, so no experiment runs on a blind witness. The payload key follows ADR-035 (proposed). Option (a), the explicit zero, stays the rule for a robot that stays co-located and stops seeing the patient (`02` section 4.7).
