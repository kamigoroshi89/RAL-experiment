## Obiettivo

Build and bench-test the emulated devices that give the lab demo fully controllable events: programmable BLE boards that emit the signals of the scenario catalogue and carry the fault and attack hooks, a BLE-to-ROS 2 gateway bridge on the ward node that publishes `Sample` and `Event` on `/ralmon/samples` and `/ralmon/events`, and one commercial device connected for realism. Output: firmware and bridge under `hardware/emulated_devices/` and the artefact `outputs/WS10-T02.md` with the fields listed in "Done when".

## Test

Verification checks:

1. The boards emit, through the BLE path and the bridge, samples whose `signal` values are `SignalId` values of `#signals`: at least `bp`, `hr_pulse`, `inflation_ms`, `cuff_health` for the cuff emulator and `hr_ecg` for the heart-rate emulator; `spo2` only if a catalogue scenario needs it.
2. On the ward node, a captured message on `/ralmon/samples` carries every field of `Sample` (`signal`, `t_device_ms`, `t_rx_ms`, `value`, `seq`, `quality`) and `t_rx_ms` is stamped by the bridge; `seq` is generated by the device, not by the bridge (except in replay and injection modes, where it follows the hook definition).
3. The bridge publishes `EventKind.MEASUREMENT`, `DEVICE_ERROR` (cuff error code) and `NODE_STATE` (BLE link lost or restored) events on `/ralmon/events`, and uses the same message types and field mapping as the simulated devices of WS07-T03.
4. Every hook required by at least one scenario of the WS10-T01 catalogue is implemented and shown by a log in `bench_logs/`: the effect is visible on `/ralmon/samples` or `/ralmon/events` and the log path is cited in the hook table.
5. The runner-visible test log (which hook was active and when) is separate from what is transmitted: no field of a transmitted frame reveals that a hook is active (the monitor must never see ground truth).
6. `timestamp_policy` matches the `clock_policy` of WS10-T01 (default: `t_device_ms` is wall-clock milliseconds since the run start, supplied by the runner in the emit command).
7. Link test: N frames sent from the board, N_rx received on `/ralmon/samples`, loss rate stated, N at least 100; path latency from emit command to the message on the topic reported as p50, p95, p99 in wall-clock milliseconds, measured on the ward node clock.
8. The commercial device is connected in a mode consistent with `patient_stand_in` and `ethics_reference` of WS10-T01: a measurement on a person only if that file permits it; otherwise connectivity, link behaviour and its own error codes only. The mode is written down.
9. Authentication and sequence numbers: each device declares whether it authenticates frames and how `seq` behaves after a restart, so that the replay scenarios can be run with and without authentication (analisi §4.5 matrix: replay is distinguishable with authentication, partly without).

## Passi

1. Read `outputs/WS10-T01.md`; list the hooks the catalogue needs and the signals each scenario reads.
2. Choose the programmable board(s) and the BLE stack; record the model and version in `board_model`. The standard BLE blood pressure profile is the message model for the cuff (analisi §5.2); record any deviation.
3. Write the cuff and heart-rate emulator firmware: emit frames on command with the value and `t_device_ms` supplied by the runner; device-owned `seq`; error-code frames; anomalous inflation durations.
4. Implement `device_control_interface` exactly as written in WS10-T01, including entering and leaving test mode.
5. Implement the hooks required by the catalogue, from this list: F1 `ble_dropout` (stop transmitting and let the link state change), F2 `stuck_at`, F3 `silent_bias`, F4 `cuff_error_code` (error code and anomalous inflation duration), F5 `replay` (retransmit stored earlier frames), F6 `plausible_injection_naive` (frames without valid sequence or authentication), F7 `plausible_injection_informed` (frames consistent on all channels, including a plausible pulse rate), F8 `timestamp_manipulation` (implausible timestamps). Rows of hooks that no scenario needs may say `implemented: no`.
6. Write the gateway bridge on the ward node: BLE receive, stamp `t_rx_ms`, publish `Sample` and `Event` with the message types WS07-T03 uses, publish `NODE_STATE` on link changes. No monitoring logic in the bridge.
7. Connect the commercial device and document its mode (check 8).
8. Bench-test: link test (check 7) and one log per implemented hook (check 4); store logs under `bench_logs/`.
9. Write `outputs/WS10-T02.md`; commit firmware and bridge with the commit message `WS10-T02: emulated devices and gateway bridge`.

## Notes

### Hand-over from ADR-035 (accepted by gab, 2026-10-09)

A frame that fails the authentication check (field `authentication_mode`) is published by the bridge as an `Event` of kind `verification` (`source` the gateway, payload `verification` = `failed`, `subject` = the device), never as a `device_error`, which carries only the cuff `error_code`. The bridge publishes an `auth` Sample only for a dispense frame whose verification passed; a device that cannot verify emits no `auth` (`#trace-schema` 0.2.0, rules 5 and 6; payload keys from the conventions table of `docs/models/evidence-channels.md`).
